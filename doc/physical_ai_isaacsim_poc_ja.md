# Physical AI PoC設計書：Isaac Sim × 実機ロボット（V-World / R-World）

**調査基準日：2026年10月22日**  
**対象**：TAMIYA 71201、DFRobot Maqueen Lite V5、エンコーダー付き4WD DIYシャーシ、NVIDIA Isaac Sim / Omniverse、ROS 2、Modelica、Rust、Python  
**目的**：実機を仮想環境に再現し、シミュレーションで検証した制御・認識を実機へ適用し、実機観測に基づいて仮想モデルと方策を更新する、小規模なPhysical AIの概念実証（PoC）を構築する。

> **評価・価格に関する注意**：ハードウェアの星評価は、一般的な製品品質ではなく「このPhysical AI PoCにどの程度向くか」の設計上の評価であり、実測性能やメーカーの公式評価ではない。価格は調査日に確認できた掲載価格。入手性は販売ページの表示に依存し、送料、電池、コネクタ、マイコン、モータードライバー等が別料金の場合がある。推定値は「見積もり」と明記する。

## TL;DR

**PoCは可能。ただし「シミュレータとロボットをつなぐ」ことと「精度のあるデジタルツインを作る」ことは別の難易度である。** 最初から高度な強化学習を実機に走らせるのではなく、計測・通信・制御の閉ループを先に成立させる。

### まず選ぶべき構成

- **一万円前後でフィードバックを学ぶ**：エンコーダー付きDagu 4WDスマートシャーシ（掲載価格4,155円）＋ESP32開発ボード＋対応電流のモータードライバー＋電池・配線。販売ページは入荷待ち表示だったため、在庫と送料を再確認する。キット自体にマイコンとモータードライバーが含まれるとは限らない。
- **履帯型ロボットを忠実に再現する**：TAMIYA 71201（17,600円）。micro:bit V2、モータードライバーmi-01、超音波センサーmi-02を含むが、単3電池2本は別売。エンコーダーが標準搭載されないため、外部カメラによる位置計測かエンコーダーの後付けを追加検討する。
- **micro:bitを既に持っている**：Maqueen Lite V5（6,369円）を候補にする。掲載品にmicro:bitと電池は含まれず、別途購入の場合は送料も含め一万円を超えやすい。
- **PC**：Isaac Simのハードウェア要件を別途確認する。2026年10月時点のNVIDIA公式ダウンロードページにはIsaac Sim 6.1.0が掲載されている。現行要件ページの最低目安はRTX 4080 / 16GB VRAM / 32GB RAM、より余裕のある構成はRTX 5080 / 64GB RAM。ロボット購入予算にPC費用は含まない。
- **実装言語**：最初はPython（Isaac Sim API・ROS 2アダプター・評価スクリプト）。Rustは安定した制御ノードが必要になった段階で追加。Modelicaはモーター／電気／機械系の同定・解析に有用だが、最初の接続PoCには必須でない。

## 1. まずPoCの成功条件を決める

「Physical AI」はここでは、物理的なロボットに作用し、センサー観測に応じて行動を選び、実機データを使ってシミュレーションや方策を改善するシステムを指す。単に3Dモデルを表示するだけでは、Physical AIの検証にはならない。

### 最小の実証タスク

1. 実機が前進・停止・旋回コマンドを受け取る。
2. 実機のエンコーダーまたは外部カメラから、実走行距離・速度・向きを記録する。
3. Isaac Simの同じコマンドに対する仮想ロボットの走行を計算し、実機軌跡と比較する。
4. 摩擦、モーター応答遅れ、左右差、センサー誤差を補正する。
5. シミュレーション内で障害物回避を検証し、制限付きで実機に適用する。
6. 実機で得た誤差からシミュレーションのパラメーターを更新する。

### 初期の合格基準（PoC目標の例）

以下は公式仕様ではなく、試験計画に使う暫定的な受け入れ目標である。1回の試験で達成できない場合は実測値を基準に調整する。

- USB通信：コマンドとテレメトリーの往復遅延を記録し、p95が100 ms以下を初期目標とする。
- 1 m直進：シミュレーションと実機の移動距離の差を15%以下にする。
- 旋回：定点旋回または90度旋回の実測角度とシミュレーション角度の誤差を測る。
- 障害物回避：同一の静的障害物コースを10回実施し、接触せず完走した割合を記録する。
- 安全：通信喪失時の停止動作を10回検証し、コマンド・ウォッチドッグが規定時間内にモーター出力を切ることを確認する。

## 3. 推奨アーキテクチャ：V-WorldとR-Worldを安全に分離する

この文書では、V-WorldをVirtual World（仮想世界＝Isaac Sim内のロボット・環境）、R-WorldをReal World（実世界＝実機と実センサー）というユーザー定義の呼称として使う。これは特定のNVIDIA製品機能名ではない。

```text
                    ┌────────────────────────────┐
                    │ PC：Python制御・学習・評価 │
                    │  policy / metrics / logger │
                    └──────────────┬─────────────┘
                                   │ 共通の高レベル指令
                      ┌────────────┴─────────────┐
                      │                           │
              ┌───────▼────────┐         ┌────────▼─────────┐
              │ V-World        │         │ R-World          │
              │ NVIDIA Isaac   │         │ 実機マイコン     │
              │ Sim / USD      │         │ ESP32 / micro:bit│
              │ 仮想センサー   │         │ PWM/ドライバー   │
              └───────┬────────┘         └────────┬─────────┘
                      │ sim観測・pose             │実測センサー・encoder
                      └────────────┬─────────────┘
                                   ▼
                    ┌────────────────────────────┐
                    │ 同定・比較・モデル更新       │
                    │ friction / motor lag / bias  │
                    └────────────────────────────┘
```

### 重要なルール

- 仮想ロボットと実機で、**指令API（例：前進速度・旋回速度）を揃える**。その下のドライバーはSimulation AdapterとHardware Adapterに分離する。
- ROS 2の名前空間・トピックを分ける。例：`/sim/cmd_vel`、`/sim/odom`、`/real/cmd_vel`、`/real/encoder_ticks`、`/real/ultrasonic_range`。同じトピックにシミュレーションと実機の指令を混ぜない。
- 通常の開発・学習では仮想機と実機を並行稼働させてもよいが、実機のモーターを動かす指令には独立した許可スイッチ、速度上限、タイムアウト、緊急停止経路を設ける。
- 実機のテレメトリーでシミュレーション状態を更新する場合は、時刻スタンプと遅延を扱う。ネットワーク遅延を無視して、単純に実機位置を毎フレーム完全同期させられると仮定しない。
- 最初のPoCではAIを使う前に、`cmd → motor → measured state → log` の実測閉ループを作る。

### ROS 2の役割

Isaac SimはROS 2 Bridge拡張を通じてROS 2トピック、サービス等をやり取りできる。NVIDIAのチュートリアルではURDFインポート、Differential Controller、Articulation Controller、ROS 2 Publisher/Subscriberを組み合わせてロボットを駆動する方法が説明されている。

ROS 2はシミュレータと実機ソフトウェアの間の標準的なメッセージ層であるが、micro:bitやESP32のファームウェアが自動的にROS 2対応になるわけではない。実機側のMCUとROS 2の間には、USBシリアル／Wi-Fi等のアダプター・ノードを実装する。

## 4. ステップごとの構築手順

### Step 0：ホスト環境を確認する

1. NVIDIAのCompatibility CheckerでGPU、ドライバー、RAM、OSを検査する。
2. 使用するIsaac Simリリースに対応したROS 2ディストリビューションとPython環境を選定する。新規環境の第一候補はUbuntu 24.04＋ROS 2 Jazzy。
3. Isaac Simの基本シーンを起動し、標準ロボットを動かす公式チュートリアルを実行する。
4. ここが失敗した場合、ロボット購入・シリアル通信へ進む前にPC／ドライバー問題を解消する。

### Step 1：実機の計測を先に作る

モーターを動かす前に、センサー値を一定周期で読み、CSVまたはROS 2トピックに保存できることを確認する。

- Dagu＋ESP32：エンコーダーのカウント、左右のPWM値、電池電圧（測定回路がある場合）、コマンド受信時刻を返す。
- Maqueen：超音波・ラインセンサー値、実行したモーター指令を出力する。回転エンコーダーがない前提では、別の位置推定手段を検討する。
- TAMIYA：micro:bitのUSBシリアル通信を利用できるが、mi-01の制御手順はTAMIYAのプログラミング資料に照らして検証する。標準搭載の障害物回避プログラムがそのまま外部APIになるわけではない。

USBシリアルは初期実装に向く。Wi-Fi／Bluetoothは便利だが、通信の不安定さを制御の不確実性に持ち込むため、初回PoCではUSBを優先する。

### Step 2：共通の制御APIとMCUプロトコルを決める

上位制御APIをたとえば次のように設計する。

```text
DriveCommand {
  timestamp_ms: integer
  seq: integer
  linear_mps: float
  angular_rps: float
  enable: boolean
}

RobotTelemetry {
  timestamp_ms: integer
  seq: integer
  left_encoder_ticks: integer?   # エンコーダーがない実機では未設定
  right_encoder_ticks: integer? # エンコーダーがない実機では未設定
  range_m: float?
  battery_v: float?
  motor_fault: boolean
}
```

MCUとのシリアルでは、最初は改行区切りCSV等の単純な形式を用いてもよい。例として `CMD,seq,left_pwm,right_pwm,enable`、応答を `TEL,seq,left_ticks,right_ticks,range_mm,battery_mv` とする。実際のメッセージ形式は自分のファームウェアに合わせて決める。

必須の実装項目：

- 範囲検証（PWM、速度、シーケンス番号）
- コマンドに時刻／シーケンス番号を付ける
- 新しいコマンドが一定時間来なければ停止するウォッチドッグ
- センサー異常・通信異常・低電圧の検出
- モーター出力とロジック回路の電源条件を確認する

### Step 3：V-Worldのロボットモデルを作成する

#### USD／URDFの役割

- **USD**：Isaac Simのシーン、マテリアル、ジオメトリ、物理属性などを扱う主要なシーングラフ形式。
- **URDF**：リンク・関節・慣性・センサー位置など、ロボットの構造を記述する形式。Isaac SimのURDF ImporterでUSDへ変換できる。
- **CAD／メッシュ**：外観の忠実度が重要な場合に利用する。最初から細かいねじや履帯一枚一枚を作らず、外形・質量・接地・駆動のモデルから始める。

#### クローラー型のモデル化

TAMIYA実機を対象とする場合、履帯全体を最初から一枚ずつシミュレートするのではなく、次の近似で始める。

1. `base_link` にボディを作り、質量・重心・慣性を概測する。
2. 左右履帯の接地領域を簡略ジオメトリで表す。
3. 左右のトラック速度を独立に変えるスキッドステア（差動駆動近似）の制御インターフェースを作る。
4. 床面摩擦と横滑りを調整し、直進・旋回データを実機と比較する。
5. 必要になってから履帯接触の精密化やクランク機構を追加する。

**重要**：標準的な2輪差動駆動コントローラーがそのまま履帯の接地物理を正確に再現するわけではない。指令の左右分配には使えても、滑り・接触摩擦・履帯の変形は別途モデル化・同定が必要。

#### 車輪型（Dagu／Maqueen）のモデル化

- `base_link`、左／右駆動部、ホイール半径、車輪間距離、センサー位置を記述する。
- 車輪型は通常の差動／スキッドステアモデルに落としやすい。
- Daguの4WDは左右のモーターをペアにして同一側として扱うことができるが、実際の配線方法、モータードライバー電流定格、左右のエンコーダー計数方法を確認する。
- 実測したホイール半径・車輪間距離と、制御に使用する有効半径／有効トレッド幅を分けて管理し、滑りによるモデル誤差を評価する。

### Step 4：ROS 2 Bridgeを使って仮想ロボットを動かす

1. Isaac SimでURDFをインポートし、USDとして保存する。
2. ロボットに適切な物理特性、関節ドライブ、センサーを設定する。
3. `isaacsim.ros2.bridge` を有効化する。
4. 仮想センサー観測をROS 2へpublishし、ROS 2コマンドをシミュレーション側でsubscribeする。
5. 同一の制御ノードを実機側にも使用できるように、シミュレーションと実機の入出力をアダプターで分離する。

NVIDIAの公式チュートリアル「Driving TurtleBot using ROS 2 Messages」は、ロボットへ指令を送る一般的な流れの参考になる。履帯では差動駆動近似を独自に調整する。

### Step 5：R-World側のROS 2アダプターを作る

MCUとROS 2は直接同じソフトウェア環境で動くとは限らない。PC側にHardware Adapterを作り、USBシリアルからテレメトリーを受信してROS 2に変換する。

例：

- MCU → PCシリアル：`TEL,...`
- Python Hardware Adapter → ROS 2：`/real/encoder_ticks`、`/real/ultrasonic_range`
- ROS 2の上位ノード → Python Hardware Adapter → MCU：`/real/cmd_vel` を左右モーター指令へ変換

現実のハードウェアで重要なのは、シミュレーターやPCの停止・遅延・クラッシュが、実機のモーターを危険な状態で動かし続けない構造である。

### Step 6：実機データでモデルを同定する

同じ指令シーケンスを実機とシミュレーションへ与え、ログを比較する。

- **直進ステップ応答**：PWMを段階的に変え、立ち上がり時間、最高速度、左右差を測る。
- **旋回**：左右の速度差を変え、旋回半径や角速度を測る。
- **惰性走行／停止**：駆動停止後にどれくらい滑るか測る。
- **センサー距離**：既知距離の障害物を使い、距離バイアス・ばらつき・最大有効距離を測る。
- **電池状態**：満充電／消耗状態で応答がどれだけ変わるかを測る。

モデル更新の順序は、まず寸法と質量、次に駆動応答、最後に摩擦・滑りとセンサー誤差にする。複数のパラメーターを同時に変更すると、どの要素が誤差を改善したか判断しづらくなる。

### Step 7：Sim-to-RealとReal-to-Simを閉じる

**Sim-to-Real**：仮想環境で検証したルール、コントローラー、学習済み方策を実機へ適用する。はじめは低速・静的障害物・監視付きに限定する。  
**Real-to-Sim**：実機ログを使い、速度応答・摩擦・センサーの偏り・通信遅延等を更新して仮想モデルを現実に近づける。

Sim-to-Realギャップを減らすため、摩擦、モーターパラメーター、電池電圧、センサー雑音、センサー取り付け誤差、コマンド遅延をランダム化して学習させる手法がある。ただし、ランダム化すれば自動的に実機で動くわけではない。実機データで妥当な範囲を決め、その範囲内で変動させる。

**同期の注意**：実機を仮想環境に反映することは、必ずしも1フレーム単位の完全同期を意味しない。時刻スタンプ、測定時刻、受信時刻、欠測、遅延をログに残し、シミュレーションの追従遅れを評価する。

## 5. センサー構成と観測可能性

| 手段 | 適した目的 | 星評価 | 制約 |
|---|---|---:|---|
| モーターエンコーダー | 左右回転数、移動距離、速度制御 | ★★★★★ | タイヤ／履帯の滑りは測れない。符号・パルス数・電気ノイズの確認が必要。 |
| 超音波距離センサー | 近距離障害物回避 | ★★★☆☆ | ビームの広がり、柔らかい／斜めの面、短距離精度に注意。Maqueen掲載仕様では搭載時5～50 cm、±5 cm。 |
| IMU（加速度・ジャイロ） | 角速度、姿勢変化の補助 | ★★★☆☆ | ドリフトがある。単独の長時間位置推定には不十分。micro:bitの内蔵センサーの利用はできるが、走行中の正確なオドメトリーの代替ではない。 |
| USBカメラ＋AprilTag／ArUco | 外部視点から位置・向きを計測 | ★★★★☆ | カメラ固定、尺度校正、マーカー見失いへの対策が必要。床面テストには実用的。 |
| RGB／深度カメラ | 視覚認識・障害物位置推定 | ★★★★☆ | データ量と計算量が増える。初期の通信PoCには過剰。 |
| LiDAR | 距離地図・SLAM | ★★★★☆ | 予算・重量・配線・取り付けが小型ロボットでは大きな課題。最初から必須ではない。 |

**このPoCの推奨順序**：Dagu＋エンコーダー → 必要に応じて超音波 → カメラによる外部姿勢推定 → RGB／深度・LiDAR。TAMIYAの形状を優先する場合は、オドメトリーの不足を固定カメラ＋視覚マーカーで補う方法がある。

## 6. Modelica・Rust・Pythonの現実的な役割分担

### Python：PoCの主言語（★★★★★）

- Isaac Sim APIでシーン、アセット、シミュレーション、ログを扱う。
- `rclpy`でROS 2ノード／アダプターを作り、シミュレーションと実機のトピックをつなぐ。
- NumPy／Pandas等でログ分析、パラメーター同定、グラフ化を行う。
- PyTorch／Isaac Lab等で方策学習へ進む際の中心言語とする。

**推奨**：初期PoCはPython主体で作る。入出力とログが安定するまでRustやModelicaを必須コンポーネントにしない。

### Rust：制御ノードやデータ層（★★★☆☆ → 追加段階では★★★★☆）

ROS 2向けRustクライアント`rclrs`が公開され、2026年9月に0.8.0が公開されている。ROS 2 Humble、Jazzy等のバインディングが扱われている一方、バージョン1.0未満のため、APIの変更を想定する。

適した用途：

- 型安全性や明確な状態管理が重要なROS 2制御ノード
- シリアルプロトコルのパーサー、ウォッチドッグ、コマンド検証
- 安定性・保守性を重視するデータ収集サービス

注意：Isaac Simの拡張やスクリプトはPython中心なので、シミュレーション側をRustに置き換える利点は小さい。マイコンファームウェアをRustで書くことも検討できるが、最初はESP32の既存SDK／Arduino系など、検証しやすいファームウェア構成から始めるのが安全。

### Modelica：物理系の解析・モデル同定（★★★☆☆）

Modelicaは機械、電気、制御等をまたぐ物理モデルを記述するのに向く。OpenModelica等を利用して、モーター、電池、ギア、摩擦、速度応答を独立にモデル化し、実機ログに合うパラメーターを調べる用途がある。

FMI（Functional Mock-up Interface）はツール間で動的モデルを交換する標準で、FMUを使ってコシミュレーション等を構成できる。OpenModelicaからFMUを書き出し、FMPy等を通じてPython側から利用する方式は考えられる。

ただし、Isaac Simが任意のModelicaモデルを無条件にネイティブ実行するという意味ではない。連成には時間刻み、入出力、ソルバー、単位系、FMUの実行環境を整える必要がある。

| コンポーネント | 主な言語 | 初期段階で必要か | 後段での価値 |
|---|---|---|---|
| Isaac Simアセット／シーン／評価スクリプト | Python | 必須に近い | シナリオ自動化・学習・ログ分析 |
| ROS 2 Hardware Adapter | Python | 推奨 | 安定後にRustへ再実装可能 |
| MCUモーター制御／ウォッチドッグ | C/C++や対応SDK（またはMicroPython） | 必須 | 高速・確実なローカル制御を維持 |
| 物理駆動系モデル | Modelica（任意） | 不要 | システム同定・マルチドメイン解析 |
| 堅牢なROS 2制御サービス | Rust（任意） | 不要 | 型安全性、構造化された非同期処理 |

## 7. 安全設計：仮想世界から実機への出力をゲートする

小型工作ロボットでも、車輪・履帯、ギヤ、配線、電池にはリスクがある。学習エージェントやシミュレータからの指令をそのまま常時実機に流さない。

1. **物理的な電源遮断／緊急停止**を用意する。OS上のボタンだけに依存しない。
2. MCU側に**コマンド・ウォッチドッグ**を実装し、通信途絶時はモーターを停止する。
3. 実機制御を許可する明示的なスイッチ／状態を置く。初期値は無効。
4. 速度・加速度・PWM・旋回をソフトウェアで制限し、まず車輪／履帯を浮かせて試験する。
5. SimとRealのトピックを分離し、テスト用コマンドが実機に誤配信されないようにする。
6. バッテリーの極性、電流定格、モータードライバーの発熱を確認し、MCUのロジック電源とモーター電源を適切に扱う。
7. 実機にAI方策を適用する前に、決定論的な停止・速度制限・非常時動作を検証する。
8. 遠隔PCやネットワーク障害に備え、モーター制御の最低限の安全機能を実機側に残す。

**デジタルツインは安全機構の代わりにならない。** シミュレーションで衝突しないと確認しても、現実の摩擦・電池・配線・遅延が同じである保証はない。

## 9. よくある落とし穴と対策

| 症状 | 主な原因 | 対策 |
|---|---|---|
| Isaac Simの起動や描画が遅い／落ちる | GPU・VRAM・ドライバー・RAM不足 | Compatibility Checker、公式のリリース別要件、最小シーンを確認。 |
| ROS 2トピックが見えない | ROSディストリビューション、DDS、環境変数、ファイアウォールの不一致 | Isaac Sim公式ROS 2インストール手順に従い、同じROS_DOMAIN_ID／通信方式で接続。 |
| MCUとUSBシリアルが不安定 | 改行処理、ボーレート、ポート権限、接続断 | 単純なテキストプロトコル、タイムアウト、シーケンス番号、ロギングを追加。 |
| Simは直進するが実機は曲がる | 左右モーター差、電池電圧、床面摩擦、滑り | 左右別のPWM→速度特性を計測し、モデルと制御に補正を入れる。 |
| センサー値は正しいのに回避しない | 座標フレーム、距離単位、時刻差、閾値設定 | m／mm、ロボット基準／世界基準を明示し、記録を可視化する。 |
| TAMIYAの実機を正確に同期できない | エンコーダーがない、独自のモータードライバーAPI | 固定カメラ＋マーカーによる位置計測、またはエンコーダーの追加を検討。 |
| RL方策が実機で破綻する | モデル誤差、観測差、アクチュエータ遅延 | 実測レンジ内でドメインランダム化し、段階的に速度とタスクを広げる。 |

## 10. 最終推奨

### 1万円前後で閉ループ制御の勉強が主目的

**エンコーダー付き車輪シャーシ＋ESP32＋適切なモータードライバー**を優先。エンコーダーにより、速度・距離・左右差を数字で測定できる。これらがないと「シミュレーションと実機の違い」が目視の感覚的比較になりやすい。ただし、Dagu製品は調査時点で入荷待ち表示だったため、購入可能性が確実な同等品を探す必要がある。

### 履帯のメカを再現することが主目的

**TAMIYA 71201**を選び、まず簡略なスキッドステアモデルから始める。実機の正確な姿勢フィードバックが必要になった段階で、固定カメラ＋マーカーまたはエンコーダー後付けを検討する。予算1万円を超えることは許容条件として扱う。

### micro:bitを既に所有している

**Maqueen Lite V5**が、低予算でセンサーを含む小型の走行プラットフォームとして有力。履帯ではないが、超音波・ラインセンサーを利用する認識・回避の最初の実験を組みやすい。

### 開発を進める順番

1. Python＋USBシリアル＋MCUで計測／駆動を成立させる。
2. USD／URDF＋Isaac Sim＋ROS 2 Bridgeを接続する。
3. 実機ログからモデルパラメーターを更新する。
4. ルールベースの障害物回避をSim-to-Realで比較する。
5. 必要になった時点でModelicaによる詳細な動力学解析、Rustによる制御ノード、強化学習を導入する。
