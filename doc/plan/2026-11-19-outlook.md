### 筋 A: 観測を増やす（エンコーダー）

- **そのまま使えるもの**: `Plant` の境界、安全ゲート、ログ形式（`Obs` に列を足す）、`sysid` の考え方。
- **買い足すもの**: エンコーダー付きのギアードモーター 2 個。例: 「120:1 ミニプラスチックギアドモーター 磁気エンコーダ付き」¥2,794（税込、1 個）。スイッチサイエンスの [10858](https://www.switch-science.com/products/10858) か [10859](https://www.switch-science.com/products/10859)（どちらがその品かは未確認）。2 個で約 ¥5,588。Robo Base の車体に付くかは**未確認**。付かなければ車体から作り直しになる。
- **最初の一歩**: ファームにエンコーダーのカウントを足し、`I` 行の末尾に 2 列増やす（取り決めを 1 行だけ拡げる）。まず静止と手回しでカウントが増えるかを見る。次に `sysid` を左右別々の K・τ で当てる。
- **やらないほうがよい理由**: ほぼ無い。強いて言えば XIAO の GPIO（D4〜D7 を I2C・UART 用に空けてある）を食う。割り込み 4 本で足りるかは推測。

### 筋 B: 学習に進む（強化学習・模倣学習）

- **そのまま使えるもの**: `Plant` を gymnasium の環境に包めば、domain randomization（`randomize.sample`）と安全ゲートがそのまま使える。
- **買い足すもの**: なし（CPU で足りる範囲）。LeRobot は 0.6.x で、主に模倣学習と画像（`doc/research/2026-11-19-software.md`）。
- **最初の一歩**: PI を「先生」にして、`Obs` から `Command` を出す小さなネットワークに模倣させる。PI に勝てないのが正しい結果で、そこから「何が足りないか」を考える。
- **やらないほうがよい理由**: 課題がヨー角速度 1 つで、PI がほぼ最適。学習が PI を超える場面が無く、**学習の価値が見えない**。速度とヨーを同時に追う、障害物を避ける、など観測と課題を増やしてからでないと題材が足りない（推測）。

### 筋 C: sim を上げる（MuJoCo の精密化・Isaac Sim）

- **そのまま使えるもの**: `mujoco_plant.py`（実機の代役に既になっている）、同定した数字、ばらつかせ方。
- **買い足すもの**: なし。Isaac Sim は GPU が要り、この PC には無い。クラウド GPU の実費は**調べていない**。
- **最初の一歩**: 実機の同定値を MuJoCo の `diffdrive.xml` に入れ戻し、実機ログと MuJoCo の gz を重ねる。合わない所（滑り・接触）を MuJoCo のパラメーターへ戻すのが、最初の物理エンジン側の R2S になる。
- **やらないほうがよい理由**: 車体が 1 自由度なので、MuJoCo の接触が効く場面がまだ少ない。Isaac Sim は 90 章の手引きで止めてよい。

### 筋 D: 無線と ROS 2

- **そのまま使えるもの**: `Command`・`Obs` はそのままメッセージに写せる（10 章）。

## 6. 筐体設計（CAD）を輪につなぐ

SolidCraft が何かは S021 が調べている。ここでは**道具に依らない受け渡し**だけを決める。どの CAD でも、質量特性の画面の数字と寸法は人が読み取れる。

### 6.1 いまの食い違い（grep と読みで確かめた）

- 寸法が 2 か所にばらばらにある。numpy の `Params` は車輪半径 0.016 m・トレッド 0.08 m、MuJoCo の `diffdrive.xml` は 0.03 m・0.10 m。K も時定数も、片方は直接の数、片方は車体の質量から出る。
- CAD を入れる前に、**寸法の唯一の置き場（寸法表）** が要る。これが CAD と輪の継ぎ目になる。
- sim の IMU は車軸の中心に固定（`SimPlant` の `ay = v·gz`）。MJCF の `imu` サイトも `pos="0 0 0"`。取り付け位置の影響は、MJCF 側でだけ試せる。

### 6.2 CAD から取れる量と入る先

| CAD の量 | 入る先 | 効くところ |
|---|---|---|
| 車輪半径 r、トレッド b | `Params.wheel_radius`・`track`、MJCF の車輪の `size`・`pos` | `ωz = r(ωR−ωL)/b`（01 章）。K_yaw に直接効く |
| 全体の質量、車体の重心位置 | MJCF の `mass`・`pos` | 慣性（下） |
| ヨー慣性 Izz（鉛直軸まわり。質量特性の画面の値と座標系に注意） | 時定数 τ（13 章の式、S020） | τ ≈ (2·Izz·r²/b² + Jw) / c（c = 停動トルク / 無負荷角速度）。MJCF では質量と形から自動で決まる |
| 電池・基板・モーターの質量と位置 | 部品表 → 平行軸の定理で Izz に足す | 置き場所だけで τ が変わる |
| IMU の位置 (x, y, z) と向き | MJCF の `site pos` と `link --axes` | 旋回中の ax・ay（下） |
| モーターの停動トルク・無負荷回転数（CAD ではなく部品表） | MJCF の `gainprm`・`biasprm`、`Params.motor_gain` | K |

### 6.3 最小の題材は 2 つ

1. **電池の置き場所 → τ**。【訂正済み。下の 6.6 を見る】0.1 kg の電池を中心から 4 cm ずらすと、S021 が MuJoCo で測ったところ τ は 0.078 → 0.090 s（約 +15 %、電池なしからは約 +25 %）。第 1 巡に書いた「+31 %、SPREAD の τ ±30 % の幅いっぱい」は、基準が小さすぎた手計算で過大だった。正しくは「SPREAD の幅の半分ほど」。それでも、置き場所の選択が τ を数 % から 10 数 % 動かすことは変わらない。
2. **IMU を旋回中心からずらす → ax**。ずれ d で、その場旋回中に ax = −ω²·d（向心）、ay = α·d（接線）。ω = 3 rad/s・d = 4 cm なら ax ≈ −0.36 m/s²。sim の加速度雑音（0.05 m/s²）より十分大きい。**IMU だけで d を逆算できる**（R2S で CAD の値を直す）。α ≈ ω/τ ≈ 15 rad/s² として ay ≈ 0.6 m/s²。MuJoCo は `site pos` を動かすだけで自動でこれを出す。【済み: S021 が確かめた。ω = 10.77 rad/s・d = 4 cm で ax = −4.643 m/s²、式の −ω²d と一致】

「CAD を変える → sim で確かめる → 作る → 測って CAD と sim を直す」の 4 歩目は、**質量をはかりで測る**（CAD の密度と造形の充填率で必ずずれる）、**同定で τ を測る**、**旋回中の ax から d を測る**。測った値は寸法表の同じ欄に `source: measured` として上書きし、CAD の値は `source: cad` のまま残す。

### 6.6 電池の位置 → τ: +31 % と +15 % の食い違いの突き止め

結論: **矛盾ではない。比べている基準が違った**。私の +31 % が過大だった。計算は `python3` で再現し、数字は S021 の `cad.py` の出力（`16-enclosure.md` 4 節）と照らした。式は 13 章の τ ≈ (2·Izz·r²/b² + Jw) / c（r = 0.03、b = 0.10、Jw = 7.2e-6、c = 0.05/30。手計算で使い、13 章の `motor.py` そのものは動かしていない）。

| | 基準の Izz [kg m²] | 4 cm ずらした Izz | 式の τ（中央 → 4 cm） | 増え方 |
|---|---|---|---|---|
| 第 1 巡（私） | 4.69e-4（箱だけ。車輪の平行軸 1.0e-4 と電池自身 6.0e-5 を入れず、電池は点） | +1.6e-4（車軸の中点まわり） | 0.055 → 0.072 s | +31 % |
| S021 の基準を車軸まわりで | 6.43e-4（箱＋車輪＋中央の電池） | +1.6e-4 | 0.074 → 0.091 s | +23 % |
| S021（`cad.py`、重心まわり） | 6.43e-4 | +1.19e-4 | 0.074 → 0.087 s | +17 % |
| S021 の MuJoCo の実測 | — | — | 0.078 → 0.090 s | +15 % |

食い違いの原因は 2 つ。
1. **基準の大きさ**。私は車輪（二つで 1.0e-4）と電池自身の慣性（6.0e-5）を落として、基準を 3 割ほど小さく見積もった。同じ増え分でも、基準が小さいと割合が大きくなる。
2. **Izz の基準点**。電池を前へ寄せると重心が約 1 cm 前へ動く。`cad.py` は重心まわりで足すので増え分が 1.6e-4 でなく 1.19e-4（差は M·x_c² = 4.1e-5）。私は車軸の中点まわりで足した。増え分の絶対値の τ への効きは、私 0.017 s、重心まわり 0.013 s、MuJoCo 0.012 s。

式（重心まわり）の +17 % は MuJoCo の +15 % と近い。残る差は 2 点で、原因は調べていない。(a) MuJoCo の τ(63 %) と式の τ の絶対値が 0.078 対 0.074 で 5 % ずれる。(b) 重心まわりと車軸まわりのどちらが差動 2 輪の「その場旋回の慣性」として物理的に正しいか。MuJoCo が重心まわりに近いのは事実だが、なぜかは確かめていない（推測: 車体が車軸の横滑りを許す向きにも動けるため）。

教訓: **相対値（%）を書くときは基準を書く**。絶対値（s）で書けば食い違いは小さかった。

### 第 5 巡で気づいた、私自身の誤り

第 1 巡の 2 節（実機の 1 週間）の 3 日目に「車輪を浮かせたまま同定のログ」と書いた。**車輪を浮かせると車体が回らず、IMU の gz はほぼ 0 になる**（台に固定されている場合）ので、同定にも閉ループの評価にもならない。訂正した。浮かせるのは、向き・ウォッチドッグ・暴走の確認だけ。`doc/bringup.md` の段 8 の「最初は車輪を浮かせて、次に床で」も、性能の評価は床だけだと一言足すとよい（推測: 同じ誤読が起きうる）。偽の XIAO は sim なので常に回り、この誤りを見つけられない。
