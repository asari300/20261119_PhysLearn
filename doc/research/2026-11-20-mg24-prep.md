## 結論（先に）

1. **今のスケッチを MG24 に書き込むと、シリアルに何も出ない見込み。** MG24 のコア 5.0.0 の `Serial` は `availableForWrite()` を持たず、基底クラスの「常に 0」が返る。スケッチは `availableForWrite() >= n` のときだけ書くので、`I` 行も `# ERR` の行も 1 本も出ない。CI の `firmware-mg24` はコンパイルしか見ないので、この不具合は CI では分からない。実機を待たずに、2 行ぶんのスケッチの直しを先に入れられる（5 節の提案 A）。
2. 確かめる 5 点のうち、`ARDUINO_XIAO_MG24` の名前（②）と `lroundf`（⑤）は問題なし。D0〜D3 の PWM（①）は出せるが、**周波数は 1 kHz 固定・デューティは 1% 刻み・同時に 3 チャンネルまで**で、nRF52840 の「約 62.7 kHz・8 bit」とは別物。IMU の電源ピンと I2C のバス（③）は、ライブラリ側のソースでは PD5 と `Wire1`。ただし I2C のピンの割り当てが、資料の間で食い違っている。
3. **MG24 の `Serial` は USB CDC ではない。** 基板上の別のチップ（SAMD11）と UART でつながり、`Serial.begin(115200)` は本当の 115200 baud になる（④）。1 行 50 文字ほどを 100 Hz で送ると、送信だけで周期の約 4 割以上を使う。
4. PC 側（`link`・`hwcheck`・`fakexiao`・sim）は、取り決め（`doc/protocol.md`）の `I`・`M`・`S`・`# ` だけを使い、ボードに依らない。変える所は無い（4 節）。
5. 実機が届いたときの確認表は 3 節。**最初の項目は「何も出ない」ことの確認**（上の 1 が当たっているかの実験）にした。

## 1. 確かめる 5 点

### ① D0〜D3 は PWM を出せる GPIO か。周波数と分解能

判定: **ソースの行で確かめた（出せる。条件つき）。**

- `D0`〜`D3` は PC0〜PC3 に当たる（`variants/xiao_mg24/arduino_variant.cpp` の 55〜58 行 `gPinNames`。`pins_arduino.h` の `D0 (0u)` 〜 `D3 (3u)`）。
- `analogWrite(pin, v)` は `PWM.duty_cycle_mode(pin, v)` を呼ぶ（`cores/gecko/wiring_analog.cpp` の 92〜95 行）。
- `PwmClass` は `sl_pwm`（GSDK の TIMER を使う PWM ドライバー）で出す。ピンへの出力は TIMER の経路を任意の GPIO に振る方式（`sl_pwm.c` の 134〜138 行）なので、PC0〜PC3 でよい。
- **周波数は 1 kHz 固定**（`pwm.h` 122 行 `duty_cycle_mode_default_freq = 1000`。`init` の呼び出しはこの値だけ、`pwm.cpp` 105 行）。`analogWrite` の経路で変える API は無い。DRV8835 の PWM の上限 250 kHz（TI のデータシート）の内側。
- 分解能: 書き込みの値の範囲は既定 8 bit（最大 255）、`analogWriteResolution` で最大 12 bit（`pwm.h` 134 行）。**ところが、タイマーに渡すのは整数の百分率**: `duty_cycle * 100 / max_value`（`pwm.cpp` 115 行、整数の割り算）を `sl_pwm_set_duty_cycle(…, uint8_t percent)`（`sl_pwm.h` 188 行、`sl_pwm.c` 303〜309 行）に渡す。つまり **1% 刻み**で、切り捨てる。
- 同時に使えるチャンネルは **3 つ**（`pwm.h` 127 行 `max_pwm_channels = 3`）。動かす側は左右で最大 2 本、0 を書く側は一瞬だけチャンネルを借りる（下の「余談」）ので足りる。足りなくなると、`init` が失敗して**何も出さずに戻る**（`pwm.cpp` の 105〜110 行）。
- 連続して違うチャンネルのデューティを変えると効かないことがあるため、コアは前の設定から **2 ms 待つ**（`pwm.h` 128 行、`pwm.cpp` 91〜93 行）。`M` を受けるたびに最大で数 ms ぶん止まりうる。
- 0 を書くとチャンネルを止める（`pwm.cpp` 126 行 `auto_deinit`）。最後の 1 本が止まるときはタイマーごと片付け、**そのピンは入力（浮いた状態）になる**（`pwm.cpp` 177 行、`sl_pwm.c` 236〜239 行）。DRV8835 の入力には約 100 kΩ の内部プルダウンがある（TI のデータシート）ので、浮いても LOW と読まれ、空転になる。ほかのピンは止めたあとも LOW を出し続ける（`sl_pwm_init` が出力・LOW にし、`sl_pwm_stop` は経路を切るだけ。`PWM_ACTIVE_HIGH = 0`、`sl_pwm.h` 107 行）。

スケッチに響く数字（計算。`(int)(|d|*255+0.5)` を百分率に切り捨てた値）:

| 指令 d | 8 bit の値 | 実際の duty |
| --- | --- | --- |
| 0.05 | 13 | 5% |
| 0.2 | 51 | 20% |
| 0.35 | 89 | **34%** |
| 0.5 | 128 | 50% |
| 0.6 | 153 | 60% |

0〜0.6 を 0.001 刻みで見ると、実際の duty は指令より最大 0.011 小さく、平均で 0.005 小さい。同定の実験（`link id`）の ±0.35 は 34% になる（約 3% 小さい）。CSV には指令の 0.35 が残るので、ゲインが約 3% 大きく見える。nRF52840（8 bit）では 0.35 → 89/255 = 34.9% で、ほぼ一致する。この差が同定の結果に出るかは【未確認】。

**余談（0 を書く側のピン）**: 前進中は IN2 側に毎回 `analogWrite(pin, 0)` が来る。そのピンにはチャンネルが無いので、`init`（GPIO の設定・TIMER の初期化）してからすぐ `stop` する（`pwm.cpp` の 100〜130 行の流れ）。`M` を 50 ms ごとに送り直すので、これが毎回起きる。動いている側の PWM の波形が乱れるかは、`TIMER_Init`（GSDK の emlib）の中身を読んでいないので【未確認】。実機で PWM の波形か、回り方の滑らかさを見る（3 節）。

### ③ IMU の電源ピンと I2C のバス

判定: **ライブラリ側はソースの行で確かめた。バスの物理的な配線は【未確認】（資料の間で食い違い）。**

- 電源ピン: `Seeed Arduino LSM6DS3` 2.0.8 の `LSM6DS3.cpp` が、MG24 のとき `PIN_LSM6DS3TR_C_POWER` を `PD5` にし（38〜40 行）、`begin()`（`beginCore`）が `pinMode(…, OUTPUT)`・`digitalWrite(…, HIGH)`・`delay(10)` を呼ぶ（73〜83 行）。コアの `gPinNames` でも PD5 は「IMU enable」（`arduino_variant.cpp` 74 行、D19 の位置）。Seeed の wiki は PD5 を HIGH にしたあと **`delay(300)`** を入れる例を載せている。ライブラリは 10 ms。**足りるかは【未確認】。**
- バス: 同じ 38〜40 行が MG24 のとき `#define Wire Wire1` にする。つまり IMU は `Wire1` で読む。スケッチは `Wire` を直接使わない（`imu.begin()` が `Wire1.begin()` を呼ぶ）ので、ここは変えなくてよい。
- `Wire1` は I2C0 で、SCL = PB3・SDA = PB2（コアの `package/slcp/xiao_mg24/sl_i2cspm_xiao_mg24_1_config.h` の 57〜66 行、と `variants/xiao_mg24/noradio/include/` の同名のファイル）。`Wire`（IMU を使わない外付け用）は I2C1 で SCL = PC5・SDA = PC4（D5・D4）。
- **食い違い**:
  - Seeed の wiki のピン表: D13 = PB02 = I2C **Clock**、D14 = PB03 = I2C **Data**。
  - コアの `pins_arduino.h` 109〜110 行: `SDA1 = D14 // PB3`・`SCL1 = D13 // PB2`（wiki と同じ向き）。
  - コアの I2C の設定（上）と `arduino_variant.cpp` のコメント（D13 = SDA1・D14 = SCL1）: SCL = PB3・SDA = PB2（逆の向き）。
  - IMU が基板上で PB2・PB3 のどちらを SDA につないでいるかは、回路図を読んでいないので【未確認】。Seeed が自社のボード向けに作ったライブラリとコアが組で動く前提だが、ソースだけでは確かめられない。**実機で `I` 行（`imu.begin()` の成功）が出るかが確かめになる。**
- I2C の速さ: 設定の `SPEED_MODE 0` = 標準モード（100 kbit/s）（`sl_i2cspm_xiao_mg24_1_config.h` 44〜49 行）。スケッチは `setClock` を呼ばない。1 サンプルは `readFloat*` を 6 回呼び、1 回ごとに別の I2C の読み出し（約 45 ビット）になるので、100 kHz では 1 サンプルで約 2.8 ms（計算。コアの待ち時間を足していない【推測】）。`Wire1.setClock(400000)` で約 0.7 ms になる見込み（`Wire.cpp` 344 行に `setClock` がある。呼べるかは【未確認】）。
- I2C アドレス 0x6A: nRF52840 Sense の基板では SA0 = GND と確かめた（`doc/research/2026-11-19-hardware.md` の S087 の訂正）。MG24 Sense でも Seeed の wiki の例が `LSM6DS3 myIMU(I2C_MODE, 0x6A)` を使う。基板の回路図は読んでいない。**MG24 の SA0 は【未確認】（wiki の例が根拠）。**

### ④ USB CDC シリアル、`Serial.begin(115200)`、`Serial.available()`

判定: **ソースの行で確かめた。USB CDC ではなく UART。`availableForWrite()` が無い。**

- MG24 のチップ自体に USB は無く、基板上の SAMD11 が USB と UART の橋渡しをする。Seeed の wiki は「XIAO のうちシリアルポート用のチップを持つのは MG24 だけ」と書く。ピン表も D11 = PA09 = `SAMD11_TX`、D12 = PA08 = `SAMD11_RX`。
- コアの `Serial` は USART0（PA8 = TX、PA9 = RX）の `UARTClass`（`Serial.cpp` の末尾、`arduino_serial_config.cpp`、`sl_iostream_usart_xiao_mg24_config.h` の 87〜96 行）。**`Serial.begin(115200)` は本当に 115200 baud**（`Serial.cpp` の `begin` → `USART_BaudrateAsyncSet`）。nRF52840 の USB CDC は baud を無視するので、取り決めの「115200 baud（CDC では実際の速さに効かない）」（`doc/protocol.md` 8 行）は MG24 では当てはまらない。
- PC 側の `link.BAUD` は 115200 なので、どちらも 115200 で合う。picocom・miniterm も 115200 にする。SAMD11 が PC 側の baud の設定に追従するかは【未確認】（wiki に書いていない）。
- フロー制御は無し（`usartHwFlowControlNone`、同設定ファイル 13 行）。PC が読まなくても送信側は止まらない見込み【推測】。
- **`Serial.availableForWrite()`**: `UARTClass`（`Serial.h` 50〜72 行）は `available`・`peek`・`read`・`flush`・`write` などを持つが、`availableForWrite` を持たない。基底の `Print`（ArduinoCore-API の `api/Print.h` 61 行）は `virtual int availableForWrite() { return 0; }`。`HardwareSerial.h`・`Stream.h` にも上書きは無い。コアの `cores/gecko/` の全ファイルを検索したわけではなく、`Serial.h`・`Serial.cpp`・上の 3 つの API ファイルだけで確かめた（`UARTClass` は `Serial.h` で全部読んだ）。
  → スケッチの 55 行（`say`）と 110 行（`sendSample`）は、MG24 では**常に偽**になり、何も書かない。
- `Serial.available()`: 呼ぶたびに UART の受信（`sl_iostream` の 32 バイトの受信バッファ。設定 15 行）から非ブロッキングで読み出し、128 バイトのリングバッファ（`Serial.h` 71 行）に移す（`Serial.cpp` 82〜86 行と `task`）。メインのループが 1 周するたびにもコアが `Serial.task()` を呼ぶ（`main.cpp` 91 行）。`M` の 1 行は約 16 バイトなので、バッファに収まる。2 行を続けて送るとき（32 バイト近く）に、送信で止まっている間の取りこぼしがありうる【推測】。`link` は 1 step に 1 行しか送らない。
- 送信は `sl_iostream_write`（`Serial.cpp` 114 行）で、バッファを持たず送り終えるまで待つ見込み【推測。`sl_iostream` の中身は読んでいない】。`I` 行は例の形で 50 文字ほど（最長 70）。115200 baud は 1 文字 10 ビットなので、50 文字で約 4.3 ms、70 文字で約 6.1 ms。I2C の約 2.8 ms と足すと 1 周期 10 ms のうち約 7〜9 ms を使う。**周期が 10 ms に収まらず、欠けが出る危険がある**（3 節の基準 `MCU 周期 平均 10 ± 0.5 ms`・`欠け 0` で見る）。
- `Serial.println(msg)` は行末が `\r\n`（`Print` の仕様）。nRF52840 の `say` と同じで、PC は `line.split()` で読むので `\r` は害にならず、`# ` 行は `I` で始まらないので読み捨てられる（`src/physlearn/link.py` の `decode_sample`、44〜52 行）。

## 4. PC 側が変わらないことの確認（`doc/protocol.md` との照合）

照合は取り決めの各項目を、ボードに依存するかで分けた。読んだのは `doc/protocol.md`、`src/physlearn/link.py`、`src/physlearn/hwcheck.py`（`BAUD`・`DUTY_MAX`・`PERIOD_MS` などの定数）。`src` と `tests` で `nRF`・`62.7`・`availableForWrite`・`XIAO_MG24` を検索して、ボード名や PWM の周波数に依る記述が 0 件であることを確かめた（検索で見つかったのはスケッチと `ci.yml` だけ）。

| 取り決め | MG24 で |
| --- | --- |
| 行の形 `I t_ms ax ay az gx gy gz` と `# ...` | 変わらない（スケッチの `sendSample` と `fixed_fmt.h` が同じ） |
| `M <left> <right>`・`S`、`DUTY_MAX = 0.6`、ウォッチドッグ 200 ms | 変わらない（スケッチ共通）。ただし `M` を受けてから実際に PWM が変わるまで、コアの待ち（最大数 ms）が入る |
| 115200 baud | **意味が変わる**。nRF52840 は USB CDC で無視されたが、MG24 は UART で本当の 115200。`link.BAUD`・picocom・miniterm はすべて 115200 で合っている。他の baud にしてはいけない |
| 周期 100 Hz（`PERIOD_US = 10000`）、`hwcheck stream` の基準 | 値は変わらない。守れるかが MG24 では怪しい（④、M6 で見る） |
| 起動直後は停止 | 変わらない（`setMotors(0, 0)` が先） |
| duty からピンへ（IN1 に PWM・IN2 = 0 など） | 変わらない。PWM の仕様だけ違う（1 kHz・1% 刻み。`protocol.md` 22 行の「PWM は 8 bit・約 62.7 kHz（nRF52 コアの既定）」は nRF52840 の話に直す） |
| 座標（基板座標）・`--axes` | 変わらない。軸の向きは実機の `hwcheck axes` で決める |
| `# ERR imu not found` | 提案 A が入れば MG24 でも出る（入れないと出ない） |
| `fakexiao`・sim・`SerialPlant` | 取り決めだけに依るので変わらない |

## 5. MG24 に切り替えるときに変える所（提案。この調査では何も変えていない）

### スケッチ `firmware/xiao_imu_drive/xiao_imu_drive.ino`

- **提案 A（必須）: `availableForWrite()` を MG24 では使わない。** nRF52840 の動作は変えない。

  ```cpp
  // MG24 コア 5.0.0 の Serial は availableForWrite() を持たず、Print の既定（常に 0）が返る。
  // 0 だと say()・sendSample() が何も書かない。UART の write は送り終えるまで待ち、フロー制御は無い
  #if defined(ARDUINO_XIAO_MG24)
  #define TX_ROOM(n) true
  #else
  #define TX_ROOM(n) (Serial.availableForWrite() >= (int)(n))
  #endif
  ```

  `say()` は `if (TX_ROOM(strlen(msg) + 3)) Serial.println(msg);`（今の `> strlen + 2` と同じ）、`sendSample()` は `if (TX_ROOM(n)) Serial.write(out, n);`。
- **提案 B（推奨）: IMU の電源の待ちを足す。** `setup()` の `imu.begin()` の前に、MG24 だけ `pinMode(PD5, OUTPUT); digitalWrite(PD5, HIGH); delay(300);`（wiki の例と同じ。ライブラリの 10 ms で足りるかは【未確認】）。
- **提案 C（M6 で周期が足りないときだけ）:** `imu.begin()` のあとに MG24 だけ `Wire1.setClock(400000);`。呼べるかは【未確認】。
- コメントの直し: 13〜16 行の PWM の説明に、MG24 は 1 kHz・1% 刻み・同時 3 チャンネルと書き足す。ヘッダーの 7〜8 行（IMU の電源ピンと I2C バス）に、MG24 は PD5 と `Wire1` と書き足す。
- 直したら CI の `firmware`（nRF52840）が今までと同じ 60,652 バイトのままであること（`#if` が nRF52840 の側を変えないこと）と、`firmware-mg24` が通ることを見る。

### Python（`src/physlearn/`）
