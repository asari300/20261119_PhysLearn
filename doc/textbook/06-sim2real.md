# 06 Sim2Real — ばらつきの下でゲインを決めて実機へ

sim で決めたゲインは、sim と少し違う実機でも動かないと困ります。
この章では、ヨー角速度の PI 制御器のゲインをモデルから計算し、パラメータをばらつかせた sim で仕様を満たす割合を見てから実機へ持っていきます。
コードは `src/physlearn/control.py` と `src/physlearn/randomize.py` です。

## 仕様（この教材で決めた数値）

0 → 3 rad/s のステップを 2 秒（dt = 0.01 s）与えて、真のヨー角速度について

| 量 | 定義 | 上限 |
|---|---|---|
| 整定時間 | 目標の ±5% に入ったきり出なくなる時刻 | 0.6 s |
| 行き過ぎ | (最大値 − 目標) / 目標 | 10 % |
| 定常偏差 | 最後の 0.5 s の平均と目標の差 | 0.05 rad/s |

実機では真値が無いので、`run()` は代わりに gz で評価します（バイアスがあるとその分ずれます）。

## 制御器

PI 制御は、誤差 e = 目標 − 測った値 に、(P) 誤差に比例した分と、(I) 誤差を時間で足し合わせた（積分した）分を足して指令にする方法です。
P は素早く応じ、I は P だけでは残る誤差（モデルのずれなどで生じる定常的なずれ）を少しずつ消します。

```
 目標 r ──→(+)── e ──→ [ PI ] ──(+)──→ u ──→ [安全ゲート] ──→ Plant ──→ gz
            ↑−                   ↑                                   │
            │              sign(r)·d (デッドバンド補償)               │
            └──────────── gz − バイアス ←─────────────────────────────┘
```

```
 e = r − (gz − bias)
 u = sign(r)·d + Kp·e + Ki·∫e dt      （積分は ±1 で止める）
 Command(left = −u, right = +u)
```

### ゲインの決め方（モデルから計算）

同定したモデルは P(s) = K_yaw / (τ s + 1)。PI の零点で極を消し（極零相殺。Kp/Ki = τ にして、モーターの遅れ τ を I の項でちょうど打ち消す）、閉ループを時定数 t_c の一次遅れにします。

```
 Kp = τ / (K_yaw · t_c)
 Ki = 1 / (K_yaw · t_c)
 → 開ループ = 1/(t_c s)、閉ループ = 1/(t_c s + 1)
```

目標値の FF（目標値から直接指令に足す項 r / K_yaw）は入れていません。入れると閉ループに零点ができ、t_c < τ のとき行き過ぎ（目標を越えて振れること）が出るためです。

### t_c の決め方（粗い探索）

`randomize.tune()` が t_c を 0.08, 0.1, 0.15, 0.2, 0.25 s で試し、ばらつかせた sim で仕様を満たす割合が最大のもの（同率なら速いもの）を選びます。
ばらつきの幅（`SPREAD`）は、公称値に対する次の範囲で一様に振ります。

| 量 | 幅 | 書き方 |
|---|---|---|
| モーターのゲイン `motor_gain` | 比で −30 % 〜 +14 % | `(-0.30, +0.14)`（下, 上） |
| モーターの時定数 `motor_tau` | 比で −14 % 〜 +60 % | `(-0.14, +0.60)`（下, 上） |
| デッドバンド `deadband` | ±0.03 | 足す量 |
| ジャイロのバイアス `gyro_bias` | ±0.02 rad/s | 足す量 |

`sample()` は `rng.uniform(1 + 下, 1 + 上)` を公称に掛けます。ゲインは下に、時定数は上に広いのは、電池が減ると K が下がり、荷物を載せると τ が延びるためです（次の節）。

`tune` が選ぶ t_c は、この幅で変わります。幅が違えば、同じ同定の値でも通過率がいちばん高い t_c が別の値になりえます。15 章の全部入りの代役は、幅を広げる前は t_c = 0.2（通過率 10 %）、今は 0.25（3 %）が選ばれます。

### 幅は測って決める

幅を当て推量で置くと、通過率の数字（「100 %」「50 %」）が何を意味するのか言えません。そこで、幅を 2 つの見方で出して並べ、**広いほうを採ります**（安全側。ただし 2 つの差を表に残します）。

- **物理から**: [13 章 6 節](13-motor-physics.md)。電池の電圧で K が、荷物で τ が動く量を式で見積もったもの。
- **実測から**: 同定を何回かして、結果のばらつきを見たもの。`python -m physlearn.compare spread` が、同定の結果（JSON か CSV）を複数読んで、ゲインと時定数は平均に対する比の (下, 上)、デッドバンドとバイアスは ± の半幅で出します（[14 章](14-fit-check.md)）。

今の値の根拠です（S041、2026-11-19）。

| 量 | 物理から | 実測から（暫定） | 採用 |
|---|---|---|---|
| `motor_gain` | (−0.30, +0.10) | (−0.186, +0.138) | (−0.30, +0.14) |
| `motor_tau` | (−0.10, +0.60) | (−0.131, +0.089) | (−0.14, +0.60) |
| `deadband` | 13 章は対称な幅のまま | ±0.006 | ±0.03（据え置き） |
| `gyro_bias` | 13 章は対称な幅のまま | ±0.000 | ±0.02（据え置き） |

- **実測は代役のログから**です。同じ機体の変わりうる場面とみなした 5 本（隠しパラメータの `HIDDEN`、式の外の現象を全部入れた `HardPlant`（[15 章](15-mismatch.md)）、電池の低下（`sag`）だけを外した全部入り、電池の低下だけ、むだ時間だけ）を同定した結果で、実機のログではありません。実機で電池や床を変えて測った値に差し替えるまでは暫定です。MuJoCo のログを混ぜると、K が 8 と 18 という別の機体の差が「ばらつき」に入って幅が (−0.41, +0.67) になるので混ぜていません。
- **物理の列には出典の弱い数字が入っています。** 13 章 6 節の電池の電圧のうち、新品 1.6 V は Energizer の手引書の例の数字（仕様値ではない）、消耗 1.1 V は出典のない仮の値で、K の下側 −30 %（消耗 4.4 V で −27 %）はこの仮定に乗っています【推測】。この表の電圧を直すと、ここも直す必要があります。
- **実測が物理より狭い所**（K の下、τ の上）は、代役に電池を使い切る場面や荷物を載せる場面を入れきれていないためと考えています【推測】。物理を採っているのはそのためです。**実測が物理より広い所**（K の上 +0.138 対 +0.10）は、代役の機体どうしの差（`HardPlant` の左右差など）が入ったためと考えています【推測。分けて測っていない】。
- 採った幅で同じ 5 本を判定すると、`motor_gain` は幅の 98 %、`motor_tau` は 94 % で、どちらも幅の内です。
- 同定を数回しかしていないと、幅を小さく見積もります。`compare spread` は実測の幅の 1.5 倍を候補として出しますが、今の `SPREAD` にはその 1.5 倍を掛けていません（広いほうを採っただけ）。
- この規則は、実機のログが取れたら実測の列を入れ替えて同じ形で回せます。実機が手元に無いので、そこは確かめていません。

## 安全ゲート

制御器と Plant の間に 1 つだけ置きます（`SafetyGate`）。sim でも実機でも同じものを通します。

- duty を ±0.6 に切る（スケッチの `DUTY_MAX = 0.6` と同じ。ゲートのほうが大きいと、ログの指令と実際に出た duty がずれて同定が狂う）
- duty の変化を 10 /s（dt = 0.01 なら 1 step 0.1）に抑える
- 指令か観測に NaN/inf がある、または |gz| > 15 rad/s なら (0, 0) にして、以後ずっと止めたまま（`tripped` に理由）

```
$ uv run python -c "
import math
from physlearn.api import Command, Obs
from physlearn.control import SafetyGate
g = SafetyGate()
o = Obs(0, 0, 0, 9.81, 0, 0, 0)
for c in [Command(1.0, -1.0)] * 3 + [Command(math.nan, 0.0), Command(0.1, 0.1)]:
    print(c, '->', g(c, o, 0.01), repr(g.tripped))
"
Command(left=1.0, right=-1.0) -> Command(left=0.1, right=-0.1) ''
Command(left=1.0, right=-1.0) -> Command(left=0.2, right=-0.2) ''
Command(left=1.0, right=-1.0) -> Command(left=0.30000000000000004, right=-0.30000000000000004) ''
Command(left=nan, right=0.0) -> Command(left=0.0, right=0.0) 'NaN/inf'
Command(left=0.1, right=0.1) -> Command(left=0.0, right=0.0) 'NaN/inf'
```

止めたあとに解除する口はわざと作っていません。止まったら、原因を見てから Plant ごと作り直します。

`control.run(plant, ctrl, gate=...)` に自分で作った `SafetyGate` を渡せます。走らせたあとに `gate.tripped` を読めば、途中で止められたかが分かります（渡さなければ既定の `SafetyGate()`）。

## 動かしてみる

通過率（下の「仕様を満たした割合」）は、公称値のまわりにばらつかせた sim のうち、仕様（整定時間・行き過ぎ・定常偏差）を満たした台数の割合です。
sim が実機に近づくと sim の側の余裕が減るので、この割合は下がることがあります（07 章）。

公称の sim と、05 章で代役のログから作った `fixed.json` のそれぞれで評価します。
`fixed.json` は次の 2 コマンドで作ります（05 章と同じもの。`sim-log` が代役 `HIDDEN` のログ `real.csv` を書き、`sysid` が同定して JSON にします）。

```
$ uv run physlearn sim-log --plant hidden real.csv
real.csv: 1700 行
$ uv run physlearn sysid real.csv --out fixed.json
gyro_bias   0.0780
gyro_noise  0.0154
yaw_gain    8.0063
deadband    0.1500
motor_tau   0.2011
drift       -0.0003
→ fixed.json
```

```
$ uv run physlearn eval -n 100
tc=0.08  kp=0.0833  ki=1.0417  deadband=0.050  bias=0.0000
ばらつき 100 台で仕様を満たした割合: 100%
$ uv run physlearn eval --params fixed.json -n 100
tc=0.2  kp=0.1256  ki=0.6245  deadband=0.150  bias=0.0780
ばらつき 100 台で仕様を満たした割合: 50%
$ uv run physlearn eval --params fixed.json --tc 0.25 -n 100
tc=0.25  kp=0.1005  ki=0.4996  deadband=0.150  bias=0.0780
ばらつき 100 台で仕様を満たした割合: 15%
```

同定した車体は公称より遅い（τ = 0.2 s）ので、同じ幅でばらつかせると仕様ぎりぎりになり、通過率が下がります。
`--tc` を 0.08 から 0.25 まで変えて、同じ 100 台で数えると次のとおりです。

| t_c [s] | 0.08 | 0.1 | 0.15 | 0.2 | 0.25 |
|---|---|---|---|---|---|
| 通過率（`fixed.json`） | 1 % | 1 % | 22 % | **50 %** | 15 % |

仕様の 3 つのどれで外れたかを台数で数えます（外れ方は重なるので、足すと 100 を超えます）。

```
$ uv run python -c "
import numpy as np
from physlearn.sim import Params, SimPlant
from physlearn.control import design, metrics, run
from physlearn.randomize import sample
p = Params.load('fixed.json')
for tc in (0.15, 0.2, 0.25):
    rng = np.random.default_rng(0); f = dict(settle=0, overshoot=0, ss_error=0)
    for i in range(100):
        m = metrics(*run(SimPlant(sample(p, rng), seed=i), design(p, tc))[1:])
        f['settle'] += m['settle'] > 0.6; f['overshoot'] += m['overshoot'] > 0.1; f['ss_error'] += m['ss_error'] > 0.05
    print(tc, f)"
0.15 {'settle': 78, 'overshoot': 20, 'ss_error': 44}
0.2 {'settle': 50, 'overshoot': 0, 'ss_error': 34}
0.25 {'settle': 85, 'overshoot': 0, 'ss_error': 27}
```

遅くすると行き過ぎは消えますが、整定 0.6 s に間に合わない台が増えます（t_c = 0.25 は 85 台）。通過率が t_c = 0.2 で最大になるのはそのためです。
定常偏差が外れる理由は、別に使い捨てのスクリプトで数えました。t_c = 0.2 で外れた 34 台のうち 25 台は、3 rad/s に要る duty（u = 3 / K_yaw + d）が上限 0.6 を超える車体です。ゲインが下がった車体では、duty が上限に当たって目標に届かないのです。
最大でも 50 % で、100 % にはなりません。100 % でないことは、仕様か車体（モーター）を見直す材料です。

## 実機へ持っていく手順

1. 05 章で実機のログから `fixed.json` を作る（上の `sim-log` と `sysid` の 2 コマンド。実機では `sim-log` の代わりに `link id`）。
2. `physlearn eval --params fixed.json` で t_c とゲインを決め、通過率を見る。
3. 実機では `python -m physlearn.link` の閉ループ用のコマンドで、同じ `YawPI` と `SafetyGate` を通して走らせる（07 章の「実機の経路で 1 周」と 03 章）。
   3 rad/s に要る duty は u = 3 / K_yaw + d です。これが 0.6 を超える車体では目標に届かないので、仕様か目標を見直します。
   最初は目標を小さくして、机の上で車輪を浮かせて試す。

3 は実機が手元に無いので **確かめていません**。

## 演習

1. `design()` に FF（u に r / K_yaw を足す）を戻し、公称の sim で行き過ぎがどう変わるか測る。
2. Python から `randomize.SPREAD` を書き換え、公称の `Params()`・t_c = 0.08 で `randomize.evaluate(p, 0.08, n=50)` を比べる。
   ゲインと時定数は `(下, 上)` で書く（例 `SPREAD["motor_tau"] = (-0.60, +0.60)`）。
   時定数の幅を (−0.14, +0.60) から (−0.60, +0.60) や (−0.14, +1.20) に広げても通過率は 100 % のまま変わらないが、ジャイロのバイアスの幅を ±0.02 → ±0.1 rad/s にすると 46 % まで下がる（n = 50 で測った）。なぜか（制御器は何を引いて誤差を作っているか）。
3. `SafetyGate(max_rate=2.0)` を作り、`Command(-0.5, 0.5)` を dt = 0.01 で何回か通して、出力の duty の増え方を見る。
   この変化率で 3 rad/s に要る duty（u = 3 / K_yaw + d）に届くまで何秒かかるか。整定時間の仕様 0.6 s に間に合うか。
   次に、そのゲインを `control.run(SimPlant(Params()), design(Params(), 0.08), gate=SafetyGate(max_rate=2.0))` に渡して、閉ループで測る（既定の `max_rate=10` と比べる）。
   手で測った結果は 整定 0.19 s・行き過ぎ 0.2 %（`max_rate=10`）に対し、整定 0.55 s・行き過ぎ 30.7 %（`max_rate=2`）で、後者は仕様 NG だった（公称の `Params()`・seed 既定）。原因は積分の溜めすぎで、確かめた: `max_rate=2` では、ヨー角速度が初めて 3 rad/s に届く 0.22 s の時点で積分が 0.456 まで溜まっていて（定常で要るのは 3 / 12 = 0.25）、そのあと 3.9 rad/s まで行き過ぎる。`max_rate=10` では 3 rad/s に届く 0.45 s の時点で積分は 0.25。duty が遅れて届く間も制御器は誤差が残っていると見て積分を増やし続ける。
